- 미학적 레퍼런스 이미지 선정 기준 없음

## 3. 박씨 반론 (원문)

> "여기서 왜 로라 촬영을 하냐? 내 스튜디오에서 작업해서 여기다 갖다 주면 되고
> 내 자동화 파이프라인 전부 다 MCP를 만들어서 여기다 붙이면 되잖아."

---

## 4. 반론 해석 — Sonnet 분석

### 핵심 지적
Sonnet이 문서 2를 평가할 때 **파파플라이가 스스로 LoRA를 학습해야 한다**고 전제하고 블로커를 지적했다. 이 전제 자체가 틀렸다.

### 실제 아키텍처 (박씨 정정)

```
[스튜디오 — parksy-image]          ← 연산/생성 레이어
  잡지 촬영 → ComfyUI → LoRA 적용 → 에셋 생성
              ↓ MCP 연동
[파파플라이 — papafly]              ← 전시/배포 레이어
  에셋 수신 → Lane A (아카이브 콘텐츠)
            → Lane B (상품 코디 레퍼런스)
```

### 박씨 반론이 맞는 이유

| Sonnet 오해 | 실제 |
|-------------|------|
| 파파플라이가 LoRA 학습 필요 | 스튜디오(parksy-image)가 이미 LoRA 보유 |
| ComfyUI를 파파플라이 내부에서 구동 | ComfyUI는 스튜디오 레이어. 파파플라이는 수신만 |
| "블로커: LoRA 없음" | 블로커 아님 — 이미 존재하는 자산을 MCP로 연결하면 됨 |

### FAB 아키텍처 원칙과의 정합

박씨의 반론은 기존 FAB 컴퓨트 아키텍처 원칙과 완벽히 일치한다:
- **저장 = GitHub/CDN** (파파플라이 역할)
- **연산 = 스튜디오 + Vast.ai** (parksy-image 역할)
- 레이어 간 경계 침범 금지

Sonnet이 이 경계를 무시하고 파파플라이에 연산 역할을 부여한 것이 오류.

## 5. 문서 2에서 살릴 것 / 버릴 것

| 항목 | 판정 | 이유 |
|------|------|------|
| Lane A/B 분리 구조 | ✅ 유효 | 파파플라이 배포 레이어 설계에 그대로 적용 |
| 아카이브 메타데이터 스키마 | ✅ 유효 | 수신된 에셋 분류에 사용 |
| "셔터만 누르면 배포" 자동화 그림 | ✅ 유효 | MCP 연동으로 구현 가능 |
| 변형적 사용 법리 | ✅ 유효 | 저작권 전략은 스튜디오 레이어에서도 동일 |
| 파파플라이 자체 LoRA 학습 | ❌ 폐기 | 스튜디오 레이어 역할. 파파플라이 범위 아님 |
| ComfyUI 파이프라인 파파플라이 내장 | ❌ 폐기 | 레이어 경계 위반 |

---

## 6. 다음 과제 (반론에서 도출)

박씨 반론의 핵심은 **MCP 연동**이다. 실제로 해야 할 것:

1. **스튜디오 → 파파플라이 MCP 설계**
   - parksy-image ComfyUI 결과물을 파파플라이 Lane A/B로 자동 라우팅
   - 메타데이터(meta.json) 함께 전송

2. **파파플라이 수신 엔드포인트 설계**
   - `archive/` 디렉토리에 Lane A 에셋 수신
   - `catalog/products/` Lane B 코디 레퍼런스 연동

3. **자동화 파이프라인 전체 MCP화**
   - 기존 박씨 파이프라인(나레이션/이미지/영상) MCP 래핑 → 파파플라이 붙이기

---

## 7. 교훈

> Sonnet은 문서를 독립적으로 평가할 때 **전체 시스템 아키텍처 컨텍스트를 놓쳤다.**
> 문서 단위 평가보다 **레포 간 역할 분리(FAB 원칙)** 를 먼저 대입해야 한다.
> 박씨의 반론은 항상 시스템 전체 그림에서 출발한다.
